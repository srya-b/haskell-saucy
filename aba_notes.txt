ABA's Use of SSIDs for !fMutlicast
===================================
ABA uses !multicast for both the instances of SBCast and for the main loop that
sends AUX messages.  SBCast requires 2 instances per round (one for T, one for
F).  Currenty, the main thread uses SSIDs with ("main", sender, round,
candidate w) and instances of SBCast use ("sbcast", sender, round, bit). 

An insight to encourage in designing UC protocols is "use/give as litte
information as possible".

Learning from Leaks
====================
The leaks can give more insightful information on what's happening in the
protcol, and, might help to infer some liveness issues.  For example, if no
parties have decided and the runqueue is empty, this would indicate something
has gone wrong in the protocol.  Determining right from wrong depends on what
kind of input generation is performed. In an environment that sparsely delivers
messages, i.e. one that ISNT'T EXPECTED TO CAUSE SOMETHING TO HAPPEN, we can't
conclude anything from the above scenario.  If, instead, the environment is
more structuresand delivered all messages (perhaps in some random order) in the
runqueue according to the stages of the protocol, then we can say that parties
should be deciding something. In such a case, you can make the determination
whether the protocol has stopped or the protocol is continuing the generate
messages but isn't making meaningful progress towards deciding anything.
